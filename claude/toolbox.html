The engineering pipeline

Matt Pocock's engineering skills aren't a menu — they're a sequence. Each stage hands its output to the next, and the whole point is that you clear the conversation between stages so context never goes stale. If you only remember one thing, remember this order.

01

Sharpen the idea

Before anything gets written down, the idea gets interrogated. These run a relentless interview that walks every branch of the decision tree, one dependency at a time, and gives you a recommended answer at each fork.

/grill-with-docs/you type it

The interview, run against a real codebase — and it leaves a paper trail, writing decision records and a glossary as you go. Start here when the work lives in a repo.

/grill-me/you type it

The same interview with no codebase and no paper trail. For sharpening a plan, pitch, or decision that doesn't live in a repo.

grillingautomatic

The underlying interview technique both of the above are built on. Fires on its own whenever you ask to stress-test your thinking.

/to-questionnaire/you type it

The inverse move: when the decision genuinely needs someone else's answer, this turns it into a questionnaire for them to fill in — grilling you about what you need back, not about the subject itself.

02

Decide the shape

Once the idea holds up, the question becomes what to build and where the boundaries go.

codebase-designautomatic

Shared vocabulary for designing modules that hide their complexity behind a small surface — where a boundary belongs, and what makes code easy for both people and agents to navigate.

domain-modelingautomatic

Pins down what the business words actually mean so everyone uses them the same way, and records architectural decisions as they're made.

prototypeautomatic

Builds a throwaway to answer one design question — now a single shareable HTML file a non-developer can open and drive. Kept on a side branch as evidence rather than deleted.

/improve-codebase-architecture/you type it

Scans for places the design could be tightened, reports them visually, then grills you through whichever one you pick. Deliberately biased toward code you're actively changing.

03

Map work too big for one sitting

Skip this stage for anything a single session can hold. It's the heaviest flow in the set and over-reaching for it is the most common mistake.

/wayfinder/you type it

Turns an effort larger than any one conversation into a shared map of decision tickets — open questions whose resolution is a decision, not a slice of build work — then resolves them one at a time until the route is clear. Hands off to stage 4 when the map clears; it does not build.

researchautomatic

Sends a background agent to investigate a question against primary sources and writes the findings into the repo. The one thing wayfinder runs in parallel rather than one-at-a-time.

04

Write it down

Turning a sharpened conversation into something another session — or another person — can pick up cold.

/to-spec/you type it

Synthesises the conversation you've just had into a spec on your issue tracker. No fresh interview — it only writes down what you already settled.

/to-tickets/you type it

Splits the spec into thin end-to-end slices, each declaring what blocks it. On a real tracker those become native blocking links, so anything unblocked can be grabbed and worked immediately.

/triage/you type it

Moves incoming issues and outside pull requests through a fixed set of states — categorise, verify, grill if unclear — and writes briefs an agent can act on without further explanation.

05

Build it

One ticket per session, clearing context between each.

/implement/you type it

Builds a piece of work from a spec or a ticket. The main event.

tddautomatic

Test-first development — write the failing test, make it pass, tidy up. Your global rules already make this mandatory for bug fixes.

diagnosing-bugsautomatic

A structured loop for bugs and slowdowns where the cause isn't obvious. As of this version it redacts secrets from every command, output, and captured artifact by default.

wizardautomatic

When a step genuinely needs a human — a dashboard click, an approval, a credential — this generates a guided script that walks you through it, opens the right pages, captures the values and writes them where they belong. It fires on its own the moment work hits something an agent can't do.

resolving-merge-conflictsautomatic

Works through an in-progress merge or rebase conflict.

06

Check it

The distinguishing idea: reviewing against the standards and against what was actually asked for are two different jobs, so they run as two separate reviewers at once.

code-reviewautomatic

Reviews everything since a chosen point on two axes in parallel — does this follow the repo's documented standards, and does it match what the originating issue asked for — then reports them side by side.

Alongside the pipeline

Not a stage — reach for these whenever the moment calls for them.

When you're lost

/ask-matt/you type it

The router. Describe your situation and it tells you which flow you're in and what to reach for. Also covers what to do at the boundary between two chunks of work — carry on, clear, hand off, delegate, or compact.

/wait-what/you type it

Two words, typed the instant a reply doesn't land. Claude re-pitches it in simplified English with the context it skipped. Naming your confusion rather than asking for brevity gets you both fewer words and the missing context.

Moving between sessions

/handoff/you type it

Compresses the conversation into a document another agent can pick up cold. Narrower than it sounds — you need it only when the work has to travel: a different tool, a different folder, a colleague, or a side task you forked off mid-flow.

/teach/you type it

Learn a concept across several sessions, using the current folder as the workspace that remembers where you got to.

Setup & authoring

/setup-matt-pocock-skills/you type it

Run once per repository. Tells the other skills where your issues live, what your triage labels are called, and where the domain docs go. The rest of the set assumes this has happened.

writing-for-agentsautomatic

How to write documents an agent will read — skills, instruction files, anything reached by a pointer. Fires whenever you're editing one. Its governing idea: don't restate what the agent could look up itself; capture only what it can't find by looking.
